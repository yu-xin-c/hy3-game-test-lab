# 播放中重开：旧回调影响新一局

在原始 Hy3 生成的 Signal Memory 上补测，未修改游戏。由源码检查提出测试假设，再用 Playwright Chromium 实测；不是自主探索发现率实验。

## 实际结果

| 操作路径 | 预期 | 实际结果 | 重复 |
| --- | --- | --- | --- |
| 菜单中重开，再等待 | 留在菜单 | menu / menu，分数 0 | 3/3 |
| 开始，等待 300ms，重开，再等待 950ms | 留在菜单，不再播放旧回合 | status=menu，但 phase=input，页面显示 Repeat | 3/3 |
| 开始，等待 300ms，重开并开始，等待 950ms，点击红色 | 新回合前 1200ms 忽略输入 | 提前进入 input，点击加 10 分、progress=1 | 3/3 |

标准来自公开需求：第一回合两个颜色，每色高亮 400ms、间隔 200ms；播放期间忽略输入。第三条路径在新回合开始后 950ms 输入，离结束还有 250ms，不是临界帧争议。所有操作通过真实按钮和 Canvas 点击，时间通过浏览器虚拟时钟推进，没有直接修改对象状态。

9 次运行无页面异常。上述玩法结果均重复出现，但完整轨迹的严格字节比较不一致：包含初始 tick 的差异。因此这里只声称问题稳定复现，不声称全部时间戳一致。

## 从现象回查生成过程

`startPlayback()` 的旧 setTimeout 链继续执行，在 game.js:86 的结束分支写入当前 `state.phase='input'`。`doReset()` 替换了 state，却没有取消旧计时器或使旧回调失效，因此旧一局会改变菜单或新一局。

对应代码精确匹配原始生成记录，来自第 3 次 Write。公开方案第 3 步描述播放计时，第 5 步描述重开，但未处理二者交叉时的旧回调。两步是相关方案位置；本轮证据不足以唯一确定最早错误方案步骤，不把 Write 3 当作推理步骤 3。

此前该游戏的 Hy3 复核认为过程正确，测试主要覆盖正常通关、输局与终局重开。新增路径说明：这些测试通过，仍可能遗漏“播放中重开”的逻辑缺陷。保留旧结论与原始批次成绩，本例作为覆盖不足的补充反例；不是新增生成样本，也不直接改变原有准确率分母。
