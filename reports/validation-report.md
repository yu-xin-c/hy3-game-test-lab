## 2. 抽样方案

正式执行前填写并冻结，不得看完失败分布后再选择好看的样本：

- clean 自动报错：100% 审核；
- clean 自动通过：按游戏家族 × 难度分层随机抽样；
- faulty/lucky-pass：按错误类型 × 难度分层，同时抽自动通过和自动失败；
- 基础设施失败：100% 区分 runner 与游戏责任；
- 随机种子和抽样脚本/hash：待填写；
- 最小每层样本量及不足处理：待填写。

## 3. 标注指南

每位审核者独立回答：

1. 终局是否符合 PRD 与 oracle？
2. 所有中间步骤是否正确？
3. 第一个有充分证据的偏离 checkpoint 是什么？
4. 根因最可能对应哪个 requirement？
5. 主错误类型是什么？
6. 当前 evidence 是否足以判断？

`evidence_sufficient=false` 时不得强迫选择首错或根因，应进入补证或裁决队列。审核者不可查看自动 `first_failure` 和预测错误类型。

## 8. 结论门

只有以下条件同时满足，才可写“定位准确率与误报率已验证”：

- [ ] 抽样方案在查看系统标签前冻结；
- [ ] 至少两名独立审核者，且盲于自动预测；
- [ ] 原始审核记录与裁决可追溯；
- [ ] 分子、分母、排除和基础设施失败均披露；
- [ ] 结果链接到同一个 run ID/commit；
- [ ] 数据规模足以支持所使用的措辞；
- [ ] oracle 泄漏审计通过。

在 pilot 阶段预期结论应保持克制，例如：“自动管线在项目自建 fixture 上复现了预设首错；由于样本量和作者偏差，尚未验证对真实生成游戏的定位准确率与误报率。”
